# Лабораторная работа №6
# Что происходит с backend-сервисом после шардирования

Анализ реальных запросов сервиса бронирования отеля на шардах из лабораторной №5:
таблица `bookings` разложена по трём PostgreSQL (`shard_0`, `shard_1`, `shard_2`) по ключу
`id_guest`, справочники `guests`, `rooms`, `roomtypes` и таблица `payments` остались в основной
базе. Каждый сценарий не только разобран, но и выполнен на этих шардах командой
`manage.py shard_queries` — все цифры ниже реальные. Эксперименты проведены 16 сентября 2026 года.

## Что получилось

| Часть | Запрос сервиса | Результат |
|---|---|---|
| 2. Single-shard | брони гостя (`GET /api/guests/{id}/bookings`) | 1 шард из 3, 8 строк, 25.7 мс |
| 3. Агрегация | `COUNT(*)` для пагинации, `top_guests` | сумма по шардам 59 771 = основная база; параллельно 18.5 мс против 64.4 мс последовательно |
| 4. JOIN | карточка брони: `bookings JOIN guests JOIN rooms LEFT JOIN payments` | на шарде: `relation "guests" does not exist`; JOIN переезжает в backend |

| 6. Отказ шарда | остановлен `shard_2` | гость 102 недоступен, гости 29604 и 101 работают, COUNT неполный |
| 7. Hot shard | модели нагрузки на реальных данных | строки 33/33/33%, но один популярный гость → 17/17/67% |

## 2. Single-Shard Query

**Запрос сервиса:** брони гостя — `GET /api/guests/{id}/bookings`, функция `list_bookings()`
с фильтром `b.id_guest = %s` ([booking_repository.py:95](../main/repositories/booking_repository.py#L95)).

```sql
SELECT id_booking, id_guest, id_room, check_in, check_out, total_price, status, created_at, updated_at
FROM bookings
WHERE id_guest = 29604
ORDER BY created_at DESC
```

**На шардах** ([sharded_booking_repository.py:46](../main/repositories/sharded_booking_repository.py#L46)):

```
router: hash(29604) % 3 → shard_1
запрос выполнен на shard_1, 8 строк, 25.67 мс, шардов затронуто: 1 из 3
проверка на остальных шардах (в реальной работе не нужна):
  shard_0: 0 строк гостя
  shard_1: 8 строк гостя
  shard_2: 0 строк гостя
```

**Почему запросу не нужно обращаться к другим шардам.** Условие запроса — равенство по
`id_guest`, а это shard key. Router кладёт запись на шард по правилу `hash(id_guest) % 3`, и
то же правило применяется при чтении: у гостя 29604 хеш `2898453285432545743`, остаток 1, значит
все его брони могли попасть только на `shard_1`. На остальных шардах их нет не потому, что мы
проверили, а по построению — router не мог их туда положить. Поэтому backend открывает одно
подключение, выполняет один SQL и получает полный результат. Это самый дешёвый тип запроса
в шардированной системе: его стоимость не зависит от числа шардов.

Таких запросов в сервисе три: брони гостя, `GET /api/bookings?guest_id=...` и создание брони
(`POST /api/bookings`, в теле есть `id_guest`).

## 3. Агрегирующий запрос

**Запрос сервиса:** `count_bookings()` — `SELECT COUNT(*) ... WHERE status = 'confirmed'`,
выполняется при каждом вызове списка броней для поля `total` в пагинации
([booking_repository.py:106](../main/repositories/booking_repository.py#L106)).

Условие по `status`, а не по shard key, поэтому подходящие строки есть на каждом шарде:

```
последовательно, шард за шардом:
  shard_0 →   19776   (35.40 мс)
  shard_1 →   20102   (15.43 мс)
  shard_2 →   19893   (13.56 мс)
  объединение в backend: сумма = 59771   суммарное время 64.38 мс
параллельно ко всем шардам: сумма = 59771   время = 18.46 мс (самый медленный шард)
для сравнения, одна нешардированная база: 59771   (18.36 мс)
```

**1. Можно ли выполнить такой запрос только на одном shard?** Нет. Один шард знает только
свои ~20 тысяч подтверждённых броней. Ответ 19 776 с `shard_0` — это не «примерно треть»,
а просто неверное число для клиента, который спрашивает, сколько всего броней в статусе
`confirmed`. Единственный случай, когда агрегация становится single-shard, — если в условии
есть shard key: `COUNT(*) WHERE id_guest = 29604` идёт в один шард.

**2. Где должны объединяться результаты?** В backend. Каждый шард возвращает частичный
результат — `COUNT` по своей части данных, — а приложение складывает три числа:
19 776 + 20 102 + 19 893 = 59 771. PostgreSQL не знает о существовании других шардов и
объединить ничего не может. Для каждой функции своё правило слияния:

| Функция | Что возвращает шард | Как объединять в backend |
|---|---|---|
| `COUNT` | count | сумма |
| `SUM` | sum | сумма |
| `MIN` / `MAX` | min / max | min / max |
| `AVG` | **нельзя брать avg** | шард отдаёт `SUM` и `COUNT`, backend делит сумму сумм на сумму счётчиков |
| `GROUP BY` | группы по своей части | группы с одинаковым ключом склеиваются по тем же правилам |

`AVG` — классическая ловушка: среднее из средних трёх шардов равно настоящему среднему только
при одинаковом числе строк на шардах. В отчёте `revenue_by_room_type` есть `AVG(total_price)`,
и на шардах его пришлось бы считать через `SUM/COUNT`.

**GROUP BY на реальном отчёте.** `top_guests()` группирует по `g.id_guest` — то есть по shard key
([report_repository.py:70](../main/repositories/report_repository.py#L70)). Все брони одного гостя
лежат на одном шарде, поэтому каждая группа целиком вычисляется на своём шарде, и склеивать
группы не нужно — нужно только выбрать лучшие среди частичных top-N:

```
  shard_0 top-3: 41231=1020000.00, 47174=1011200.00, 1941=980800.00
  shard_1 top-3: 46133=1064400.00, 2333=1007000.00, 13886=980000.00
  shard_2 top-3: 42043=1149200.00, 23698=1057800.00, 7390=1028800.00
  merge в backend → top-3: 42043=1149200.00, 46133=1064400.00, 23698=1057800.00
```

А `revenue_by_room_type` группирует по типу номера — не по shard key. Брони одного типа номера
разбросаны по всем шардам, и каждая группа собирается из трёх частичных: суммы складываются,
`AVG` пересчитывается.

**3. Что происходит со временем выполнения при увеличении количества шардов?**
Зависит от того, как backend опрашивает шарды:

- **Последовательно** — время равно сумме: 35.4 + 15.4 + 13.6 = **64.4 мс**, втрое дольше
  нешардированной базы (18.4 мс). С десятью шардами будет десять слагаемых.
- **Параллельно** — время равно самому медленному шарду: **18.5 мс**, как у одной базы. Рост числа
  шардов почти не увеличивает время, пока хватает соединений и потоков.

Но даже в параллельном варианте есть цена: каждый распределённый запрос занимает по одному
соединению и по одному выполнению на **каждом** шарде. Один `COUNT` для пагинации — это теперь
три запроса к трём серверам вместо одного. Растёт не задержка, а суммарная работа системы и
число соединений, и её ограничивает самый медленный или самый загруженный шард.

## 4. JOIN между shard'ами

**Запрос сервиса:** карточка брони `GET /api/bookings/{id}`, функция `get_booking()`
([booking_repository.py:119](../main/repositories/booking_repository.py#L119)):

```sql
SELECT b.*, g.last_name, g.first_name, r.room_number, rt.name,
       COALESCE(SUM(p.amount) FILTER (WHERE p.status = 'success'), 0) AS paid_amount
FROM bookings b
JOIN guests g       ON g.id_guest = b.id_guest
JOIN rooms r        ON r.id_room = b.id_room
JOIN roomtypes rt   ON rt.id_type = r.id_type
LEFT JOIN payments p ON p.id_booking = b.id_booking
WHERE b.id_booking = %s
GROUP BY ...
```

**Где находятся связанные данные:**

| Таблица | Где лежит |
|---|---|
| `bookings` | шарды `shard_0/1/2` — по `id_guest` |
| `guests` | основная база |
| `rooms`, `roomtypes` | основная база |
| `payments` | основная база |

То есть каждый JOIN этого запроса соединяет таблицу на шарде с таблицей на другом сервере.

**Эксперимент:**

```
бронь 65974 лежит на shard_1; guests и rooms — только в основной базе
попытка выполнить JOIN сервиса одним SQL прямо на шарде:
  relation "guests" does not exist
как приходится делать: два запроса и склейка в backend
  shard_1: бронь 65974  +  default: гость «Иванов Алексей», комната G190  (6.91 мс, 2 дополнительных запроса)
оплата брони 65974 берётся из основной базы отдельно: 0
```

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?** Обычный JOIN
невозможен: PostgreSQL соединяет таблицы внутри одного сервера, а таблицы `guests` на шарде
физически нет. Сервер отвечает `relation "guests" does not exist`. Сам факт, что бронь и гость
лежат на разных серверах, превращает одну операцию БД в несколько операций приложения.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?** Нет. Одному
серверу доступны только его таблицы. Варианты обхода — `postgres_fdw` (шард подключается
к основной базе как к внешней таблице, но JOIN всё равно тянет данные по сети), либо
**копирование справочников** на каждый шард, либо **JOIN в приложении**, как сделано здесь:
backend взял бронь с `shard_1`, затем гостя и комнату из основной базы и собрал ответ сам.

**3. Какие данные пришлось бы передавать между shard'ами?** Для карточки брони — ключи
`id_guest`, `id_room`, `id_booking` с шарда и найденные по ним строки `guests`, `rooms`,
`payments` из основной базы: два-три дополнительных запроса на каждую карточку. Для списка
из 20 броней это уже 20 гостей и 20 комнат — либо 40 запросов, либо один `WHERE id IN (...)`
на каждую таблицу. Для отчёта `top_guests` — все брони с каждого шарда пришлось бы
соединять с 50 тысячами гостей; либо каждый шард отдаёт агрегаты по `id_guest`, а backend
подтягивает имена только для победителей.

**4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного shard?**
Да, если шардировать **связанные таблицы одним ключом** — это называется co-location.
Если `guests` шардировать по `id_guest` тем же router'ом, гость и все его брони окажутся
на одном шарде, и JOIN `bookings ⋈ guests` станет локальным. Таким же образом можно положить
рядом `payments` — у платежа есть `id_booking`, а через бронь известен `id_guest`. Но `rooms`
и `roomtypes` привязать к гостю нельзя: одну комнату бронируют тысячи гостей с разных шардов.
Для таких маленьких справочников (305 комнат, 3 типа) правильное решение — **реплицировать
их на каждый шард целиком**, тогда JOIN с ними тоже локальный. Итог: с ключом `id_guest`
локальными можно сделать все JOIN'ы карточки брони, кроме случая, когда справочники не
скопированы.

Есть и JOIN, который никаким выбором ключа не спасти: `find_overlapping()` ищет брони
**комнаты** на пересекающиеся даты (`WHERE id_room = ?`). Брони одной комнаты принадлежат
разным гостям и лежат на всех шардах — проверка занятости при создании брони обязана
опросить все три сервера.

## 5. ORDER BY + LIMIT

**Запрос сервиса:** лента броней `GET /api/bookings` — `list_bookings()` без фильтра по гостю:

```sql
SELECT ... FROM bookings ORDER BY created_at DESC LIMIT 20 OFFSET 0
```

**Эксперимент:**

```
  shard_0 → top-20, самая свежая 2026-09-14 14:25:17   (33.35 мс)
  shard_1 → top-20, самая свежая 2026-09-14 14:30:37   (13.83 мс)
  shard_2 → top-20, самая свежая 2026-09-14 14:26:45   (13.70 мс)
  merge 3×20 = 60 строк → top-20
  совпадает с одной нешардированной базой: True

откуда взялись настоящие top-20:
  shard_0: 6 из 20
  shard_1: 9 из 20
  shard_2: 5 из 20
  → взяв top-20 только с shard_1, получили бы верных 9 из 20, остальные 11 — не самые свежие брони
```

**Почему недостаточно получить первые 100 записей только с одного shard?** Потому что
сортировка идёт по `created_at`, а разложены данные по `id_guest` — эти поля никак не связаны.
Самые свежие брони принадлежат случайным гостям и лежат на случайных шардах: в эксперименте
настоящие 20 самых свежих распределились как 6 / 9 / 5. Top-20 одного шарда — это 20 самых
свежих броней **его гостей**, среди которых верных всего 9, а 11 «свежих» на самом деле старее
броней с других шардов.

Правильный алгоритм — тот, что в схеме методички: **каждый шард отдаёт свой top-N**
(20 строк, а не всю таблицу), backend сливает 3 × 20 = 60 строк и берёт 20 лучших. Merge
совпал с эталоном из нешардированной базы. Столько же нужно запрашивать с каждого шарда,
меньше нельзя: в худшем случае все 20 самых свежих окажутся на одном шарде.

Дополнительная цена — пагинация с `OFFSET`. Для страницы 50 (`LIMIT 20 OFFSET 980`) каждый
шард должен вернуть **первые 1000** строк, потому что неизвестно, сколько из его строк попадут
в глобальные первые 980: backend получает 3 000 строк, чтобы отдать 20. Чем глубже страница,
тем дороже, — поэтому в шардированных системах переходят на keyset-пагинацию
(`WHERE created_at < последняя_на_странице`).

## 6. Отказ одного shard

**Эксперимент:** остановлен контейнер `booking_shard_2`.

```
  shard_0: доступен, 99482 строк (17.3 мс)
  shard_1: доступен, 100574 строк (7.1 мс)
  shard_2: НЕДОСТУПЕН — connection to server at "localhost", port 5442 failed: Connection refused

  брони гостя 29604 (shard_1): OK, 8 строк
  брони гостя 101 (shard_1): OK, 9 строк
  брони гостя 102 (shard_2): ошибка — connection ... port 5442 failed: Connection refused

  COUNT(*) по всем шардам: неполный результат 200056 — недоступны shard_2
```

После `docker start` шард вернулся через 1 секунду, данные целы: 99 948 строк.

**1. Какие данные становятся недоступны?** Брони гостей, у которых `hash(id_guest) % 3 = 2`:
это 99 948 броней (33.3%) и 16 628 гостей. Не «треть каждого гостя», а полностью все брони
трети гостей, а остальные две трети гостей не затронуты вообще.

**2. Какие endpoint'ы перестанут работать?** В шардированном варианте сервиса:

| Endpoint | При отказе `shard_2` |
|---|---|
| `GET /api/guests/{id}/bookings`, `POST /api/bookings`, `GET /api/bookings?guest_id=` | работают для гостей `shard_0/1`, **ошибка для гостей `shard_2`** |
| `GET /api/bookings` — лента с `ORDER BY ... LIMIT` | **ошибка или неполный список**: треть свежих броней недоступна |
| `count_bookings` — `total` для пагинации | **неполный**: 200 056 вместо 300 004 |
| `GET /api/bookings/{id}` — по `id_booking` | нужно опросить все шарды: для брони на `shard_2` — ошибка |
| проверка занятости комнаты при создании брони | **ошибка для всех**: брони комнаты есть на каждом шарде, без `shard_2` нельзя гарантировать, что комната свободна |
| отчёты `revenue_by_room_type`, `top_guests` | **неполные** или ошибка |
| `GET /api/rooms`, `/api/room-types`, `/api/services`, `/api/guests` | работают — справочники в основной базе |

В текущем проекте API читает основную базу, и `GET /api/guests/102/bookings` во время
эксперимента вернул HTTP 200 — но это заслуга не шардирования, а того, что рабочие endpoint'ы
на шарды ещё не переведены.

**3. Продолжит ли работать остальная часть сервиса?** Частично — и это главный плюс
шардирования перед одной базой, где отказ означал бы 100% простоя. Две трети гостей
обслуживаются полностью. Но всё, что требует обхода всех шардов, деградирует: лента, счётчики,
отчёты и особенно **создание любой брони**, потому что проверка занятости комнаты — cross-shard.

**4. Что должен делать backend при обращении к недоступному shard?**

- **Single-shard запрос:** не ждать долго (короткий таймаут подключения), не повторять
  бесконечно, вернуть клиенту честную ошибку `503 Service Unavailable` с понятным сообщением,
  а не `500`. Повторные попытки — с паузой и ограничением, чтобы не добить поднимающийся шард.
- **Распределённый запрос:** решить заранее, что лучше — ошибка или частичный ответ.
  Для отчёта допустим частичный результат с пометкой «данные `shard_2` недоступны»;
  для `total` в пагинации — тоже. Для проверки занятости комнаты частичный ответ **недопустим**:
  лучше отказать в создании брони, чем создать двойную.
- **Не делать вид, что всё хорошо:** команда `shard_queries failure` именно так и помечает
  результат — `неполный результат 200056 — недоступны shard_2`.
- **Circuit breaker:** после нескольких отказов на время перестать обращаться к шарду,
  чтобы не тратить соединения и таймауты на каждом запросе.

**5. Как можно повысить отказоустойчивость?**

- **Реплика у каждого шарда** — ровно то, что сделано в лабораторной №4 для основной базы.
  При отказе Primary шарда чтение переключается на его реплику, а после promotion — и запись.
- **Автоматическое переключение** (Patroni и подобные) вместо ручного `docker start`.
- **Таймауты, повторы и circuit breaker** в backend, как описано выше.
- **Мониторинг и алерты** на недоступность шарда — по образцу проверки партиций из лабораторной №3.
- **Меньше cross-shard операций:** чем больше запросов single-shard, тем меньше endpoint'ов
  зависит от каждого отдельного шарда.

## 7. Hot Shard

Ситуация из методички — 10% / 15% / 75% запросов — при том, что строк на шардах поровну.

**Возможные причины применительно к сервису:**

| Причина | Как проявилась бы у нас |
|---|---|
| неудачный shard key | ключ `created_at`: все новые брони и все запросы «что забронировали сегодня» шли бы на один шард |
| неравномерное распределение данных | при ключе `id_room` и 305 значениях шарды получили бы по-разному; при `id_guest` разброс 0.6% — не причина |
| популярный пользователь | корпоративный клиент с тысячами броней целиком лежит на одном шарде |
| определённый тип запросов | если гости одного шарда чаще открывают свои брони, чем другие; или тяжёлые отчёты бьют по одному шарду |

**Измерения на реальных данных:**

```
строки по шардам: shard_0 99482 (33.2%), shard_1 100574 (33.5%), shard_2 99948 (33.3%)

модель 1: запросы ∝ активным броням гостя (status pending/confirmed)
  shard_0 33.1%, shard_1 33.5%, shard_2 33.5%

модель 2: один популярный гость даёт половину всех запросов
  самый активный гость 42043 (18 броней) лежит на shard_2
  → shard_0 16.6%, shard_1 16.8%, shard_2 66.7%

модель 3: запросы без shard key (лента, отчёты) — идут на все шарды
  каждый такой запрос нагружает все три шарда сразу
```

**Почему равное количество строк на shard'ах ещё не означает равномерную нагрузку?**
Потому что хеш выравнивает **число строк**, а нагрузку создают **запросы**, и они распределены
по данным неравномерно. Строка строке рознь: одна бронь читается раз в год, другая — тысячу раз
в день. В модели 2 один гость с 18 бронями из 300 004 — это 0.006% строк, — превращает
`shard_2` в горячий с 66.7% запросов, хотя строк на нём по-прежнему треть. Нагрузка зависит
от того, **чьи** данные лежат на шарде и **как часто** их запрашивают, а не от того, **сколько**
их. Хеш этого не видит: он знает только значение ключа.

Модель 3 добавляет обратный эффект: распределённые запросы вообще не зависят от размещения
и нагружают все шарды одновременно, поэтому чем больше в сервисе cross-shard запросов, тем
меньше смысла в равномерном распределении данных.

## 8. Итоговый анализ shard key

**Подходит ли `id_guest` для сервиса бронирования?** Да — с оговоркой, что у сервиса два разных
класса запросов, и ключ обслуживает только один из них. Для операций «гость и его брони» ключ
хорош; для операций «комната и её брони» и для общих списков он ничего не даёт.

### Плюсы — что стало single-shard

| Запрос | Почему в один шард |
|---|---|
| `GET /api/guests/{id}/bookings` | фильтр по `id_guest` |
| `GET /api/bookings?guest_id=` | фильтр по `id_guest` |
| `POST /api/bookings` — вставка | `id_guest` известен до записи |
| `top_guests` — GROUP BY по гостю | группа целиком на одном шарде |
| JOIN `bookings ⋈ guests`, `⋈ payments` | станут локальными, если шардировать `guests` и `payments` тем же ключом |

Данные распределились ровно (±0.6%), горячих ключей в данных нет.

### Минусы — что стало распределённым

| Запрос | Почему во все шарды |
|---|---|
| `GET /api/bookings` — лента с `ORDER BY created_at` | сортировка не по shard key: merge top-N |
| `count_bookings` — `total` для пагинации | сумма частичных COUNT |
| `GET /api/bookings/{id}` | `id_booking` не shard key: нужен обход шардов или таблица «бронь → шард» |
| `find_overlapping` — занятость комнаты | брони комнаты у разных гостей на разных шардах |
| `GET /api/rooms/{id}/bookings` | по `id_room` |
| `revenue_by_room_type` | GROUP BY по типу номера: частичные агрегаты + пересчёт AVG |
| `list_payments` — JOIN `payments ⋈ bookings ⋈ guests` | брони на шардах, платежи в основной базе |
| `PUT /api/bookings/{id}` со сменой гостя | бронь физически переезжает на другой шард |

### Проблемные операции

| Операция | Сложность | Почему |
|---|---|---|
| **JOIN** | высокая | таблицы на разных серверах: `relation "guests" does not exist`; нужен JOIN в приложении, копирование справочников или co-location |
| **aggregation** | средняя | частичные результаты + слияние в backend; `AVG` нельзя усреднять; сложность растёт с числом шардов |
| **ORDER BY + LIMIT** | средняя | top-N с каждого шарда и merge; `OFFSET` умножает объём на число шардов |
| **migration** | высокая | изменение схемы применяется к каждому шарду отдельно и должно быть согласовано; лабораторная №5 показала, что смена числа шардов при `hash % N` переносит 75% данных |
| **backup** | высокая | три базы + основная, снимки в разное время — согласованной точки восстановления нет |
| **восстановление** | высокая | восстановить один шард из бэкапа — значит вернуть его в прошлое относительно других: брони гостя есть, а платежи в основной базе — уже за более позднее время |
| **балансировка** | высокая | перенос данных между шардами при перекосе, с переключением router на лету |

Самые тяжёлые — **JOIN** (ломается на уровне SQL) и всё, что связано с **согласованностью
между шардами**: миграции, бэкап, восстановление, транзакции через несколько шардов
(создать бронь на шарде и платёж в основной базе атомарно уже нельзя).

### Вывод

Если проектировать систему заново, я бы **оставил `id_guest`**, но шардировал бы по нему
не одну таблицу, а группу: `guests`, `bookings`, `payments` и `bookingservices` — всё, что
принадлежит гостю, — а справочники `rooms`, `roomtypes`, `services` копировал бы на каждый шард.
Тогда карточка брони, брони гостя, платежи гостя и создание брони стали бы single-shard
целиком, включая JOIN'ы. Единственный принципиально cross-shard запрос при этом — проверка
занятости комнаты; для него я бы завёл отдельную небольшую таблицу «комната → занятые
интервалы» в основной базе, обновляемую при каждой брони.

Альтернатива `id_room` решила бы занятость комнаты, но сломала бы всё, что связано с гостем:
брони одного человека разлетелись бы по всем шардам, а таких запросов в API большинство.
Ключ выбирается под самые частые запросы, и у сервиса бронирования это запросы гостя.

## Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?** Single-shard содержит в условии
shard key, поэтому router заранее знает единственный шард с ответом: один запрос, одно
соединение, стоимость не зависит от числа шардов (брони гостя — 1 из 3). Distributed query
не содержит shard key: его нужно отправить на все шарды и объединить частичные результаты
в backend (COUNT для пагинации — 3 запроса и сумма).

**2. Почему JOIN между shard'ами сложнее обычного JOIN?** Обычный JOIN выполняет один сервер
внутри одной базы, используя индексы и память. Если таблицы на разных серверах, ни один из них
не видит вторую таблицу — на шарде JOIN с `guests` падает с `relation "guests" does not exist`.
Приложению приходится делать несколько запросов и соединять результаты самому, передавая
данные по сети.

**3. Как выполнить COUNT(*) по всем shard'ам?** Отправить `COUNT(*)` на каждый шард
(лучше параллельно) и сложить в backend: 19 776 + 20 102 + 19 893 = 59 771. Параллельно
это заняло 18.5 мс — как одна база, последовательно — 64.4 мс.

**4. Почему ORDER BY ... LIMIT требует объединения результатов?** Порядок сортировки не связан
с ключом распределения: самые свежие брони лежат на всех шардах (6 / 9 / 5 из top-20). Нужно
взять top-N с каждого шарда и слить их в backend; top-N одного шарда дал бы 9 верных из 20.

**5. Что произойдёт при отказе одного shard?** Данные его ключей недоступны (у нас — 33% броней,
16 628 гостей), single-shard запросы к остальным работают, а все распределённые запросы
становятся неполными или падают, в том числе проверка занятости комнаты — то есть создание
любой брони. Backend должен отвечать 503 с таймаутом, а не зависать.

**6. Что такое hot shard?** Шард, на который приходится непропорционально большая доля
запросов при равной доле данных. Причина — не размер, а популярность его ключей: один гость
с 18 бронями в модели дал шарду 66.7% нагрузки.

**7. Почему выбор shard key влияет на JOIN?** JOIN локален только тогда, когда обе соединяемые
записи лежат на одном шарде, а это определяется ключом. Если `guests` и `bookings` шардировать
одним `id_guest`, гость и его брони окажутся вместе; при ключе `id_room` — никогда.

**8. Какие операции особенно плохо подходят для распределённых данных?** JOIN между
шардированными таблицами, агрегации и сортировки без shard key, транзакции через несколько
шардов, уникальные ограничения на не-ключевых полях, `OFFSET`-пагинация, а также миграции,
бэкап и восстановление, требующие согласованности всех шардов.

**9. Что произойдёт при изменении количества shard'ов?** При `hash % N` пересчитывается адрес
почти всех записей: 3 → 4 переносит 75% данных (лабораторная №5), и на время переноса router
должен знать оба размещения. Consistent Hashing снижает перенос до доли нового шарда.

**10. Чем шардирование отличается от репликации?** Реплика хранит **полную копию** данных
и масштабирует чтение (лабораторная №4: любая реплика ответит на любой запрос). Шард хранит
**часть** данных и масштабирует объём и запись: запрос идёт только туда, где лежит запись.
Реплика не помогает, когда данные не помещаются на один сервер; шардирование не помогает
от отказа — для этого каждому шарду нужна своя реплика.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?** Само по себе — нет:
запрос броней гостя на шарде занял 25.7 мс, столько же, сколько занял бы на одной базе с тем
же индексом. Ускорение возможно косвенно: шард в три раза меньше, его индексы и данные
лучше помещаются в память, а параллельные части распределённого запроса выполняются
одновременно. Но распределённый запрос по сумме работы всегда дороже, чем тот же запрос
к одной базе: COUNT — три выполнения вместо одного.
