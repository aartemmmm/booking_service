## Часть 1. RANGE PARTITIONING по дате

```sql
CREATE TABLE lab3.events (
    id         BIGINT NOT NULL,
    user_id    BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload    TEXT,
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_09_09 PARTITION OF events FOR VALUES FROM ('2026-09-09') TO ('2026-09-10');
CREATE TABLE events_2026_09_10 PARTITION OF events FOR VALUES FROM ('2026-09-10') TO ('2026-09-11');
CREATE TABLE events_2026_09_11 PARTITION OF events FOR VALUES FROM ('2026-09-11') TO ('2026-09-12');
```

Загружено 300 000 строк, равномерно распределённых по трём дням.

```sql
SELECT tableoid::regclass AS partition_name, COUNT(*)
FROM events GROUP BY tableoid ORDER BY partition_name;
```

| partition_name | count |
|---|---|
| events_2026_09_09 | 100 239 |
| events_2026_09_10 | 99 690 |
| events_2026_09_11 | 100 071 |

### Задание

**1. В какую партицию попадёт запись с `created_at = '2026-09-10 12:00:00'`?**

В `events_2026_09_10` — проверено вставкой:

```
INSERT INTO events VALUES (900001, 1, 'click', 'test', '2026-09-10 12:00:00');
SELECT tableoid::regclass FROM events WHERE id = 900001;  -->  events_2026_09_10
```

Значение попадает в интервал `['2026-09-10 00:00:00', '2026-09-11 00:00:00')`.

**2. В какую партицию попадёт запись с `created_at = '2026-09-11 00:00:00'`?**

В `events_2026_09_11`, а не в предыдущую. Полночь 11 сентября — это нижняя граница третьей
партиции, а нижняя граница включается.

**3. Что произойдёт, если вставить запись за 2026-09-12?**

Вставка завершится ошибкой, потому что подходящей партиции не существует:

```
ERROR:  no partition of relation "events" found for row
DETAIL:  Partition key of the failing row contains (created_at) = (2026-09-12 10:00:00).
```

Это и есть главный операционный риск партиционирования по дате: если партиции на будущее
не созданы заранее, приложение начнёт падать на `INSERT`. Именно из-за этого нужны
задания 10 и 11 — автоматическое создание партиций и контроль их наличия.

**4. Почему граница `TO ('2026-09-11')` не включает эту дату?**

Потому что в PostgreSQL границы RANGE-партиции задают полуинтервал `[FROM, TO)`: нижняя
граница включается, верхняя — нет. Реальные границы видны в каталоге:

```sql
SELECT c.relname, pg_get_expr(c.relpartbound, c.oid)
FROM pg_class c JOIN pg_inherits i ON i.inhrelid = c.oid
WHERE i.inhparent = 'lab3.events'::regclass;
```

```
events_2026_09_09 | FOR VALUES FROM ('2026-09-09 00:00:00') TO ('2026-09-10 00:00:00')
events_2026_09_10 | FOR VALUES FROM ('2026-09-10 00:00:00') TO ('2026-09-11 00:00:00')
events_2026_09_11 | FOR VALUES FROM ('2026-09-11 00:00:00') TO ('2026-09-12 00:00:00')
```

Такая схема удобна тем, что соседние партиции стыкуются без зазоров и без пересечений:
верхняя граница одной буквально равна нижней границе следующей. Если бы обе границы
включались, значение полуночи принадлежало бы сразу двум партициям. Проверено: запись
с `created_at = '2026-09-10 23:59:59.999999'` попала в `events_2026_09_10` — это последнее
значение, которое ещё входит в партицию.

## Часть 2. Partition pruning

### Запрос по ключу партиционирования

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';
```

```
Aggregate  (actual time=8.373..8.374 rows=1 loops=1)
  Buffers: shared hit=932
  ->  Seq Scan on events_2026_09_10 events  (actual time=0.002..5.941 rows=99690 loops=1)
        Filter: ((created_at >= '2026-09-10') AND (created_at < '2026-09-11'))
        Buffers: shared hit=932
Planning Time: 0.305 ms
Execution Time: 8.387 ms
```

- **Сколько партиций PostgreSQL проверил:** одну.
- **Какая партиция действительно нужна:** `events_2026_09_10`.
- **Удалось ли исключить остальные:** да, обе соседние отброшены.
- **Где в плане видно pruning:** в плане нет узла `Append` — вместо него сразу `Seq Scan`
  по единственной партиции `events_2026_09_10`. Имена `events_2026_09_09` и `events_2026_09_11`
  в плане не встречаются вообще. Косвенное подтверждение — `Buffers: shared hit=932`,
  то есть прочитана примерно треть данных таблицы.

### Запрос не по ключу партиционирования

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

```
Finalize Aggregate  (actual time=7.175..8.785 rows=1 loops=1)
  Buffers: shared hit=2805
  ->  Gather (Workers Launched: 2)
     ->  Partial Aggregate
        ->  Parallel Append  (actual time=0.005..5.474 rows=25018 loops=3)
              Buffers: shared hit=2805
           ->  Parallel Seq Scan on events_2026_09_09  (Rows Removed by Filter: 25014)  Buffers: shared hit=937
           ->  Parallel Seq Scan on events_2026_09_11  (Rows Removed by Filter: 37519)  Buffers: shared hit=936
           ->  Parallel Seq Scan on events_2026_09_10  (Rows Removed by Filter: 74866)  Buffers: shared hit=932
Execution Time: 8.819 ms
```

### Сравнение планов

| Метрика | По `created_at` | По `event_type` |
|---|---|---|
| Узел плана | `Seq Scan` по одной партиции | `Parallel Append` по трём |
| Партиций прочитано | 1 из 3 | 3 из 3 |
| Buffers | **932** | **2805** |
| Execution Time | 8.387 мс | 8.819 мс |

**Почему второй запрос может обращаться ко всем партициям?**

Потому что таблица разделена по `created_at`, а фильтр наложен на `event_type`. PostgreSQL
знает границы партиций только по ключу партиционирования — по нему он может доказать, что
в партиции за 9 сентября не может быть строк за 10-е. Про распределение `event_type`
границы партиций не говорят ничего: события типа `click` могут лежать в любом дне, поэтому
исключить ни одну партицию нельзя и приходится читать все. Ровно в три раза больше буферов,
что и видно в замерах.

## Часть 3. RANGE PARTITIONING по числовому значению

```sql
CREATE TABLE lab3.products (
    id BIGINT NOT NULL, name TEXT NOT NULL, price NUMERIC NOT NULL
) PARTITION BY RANGE (price);

CREATE TABLE products_cheap     PARTITION OF products FOR VALUES FROM (0)    TO (100);
CREATE TABLE products_medium    PARTITION OF products FOR VALUES FROM (100)  TO (1000);
CREATE TABLE products_expensive PARTITION OF products FOR VALUES FROM (1000) TO (MAXVALUE);
```

### В какие партиции попали товары

| partition_name | id | name | price |
|---|---|---|---|
| products_cheap | 1 | Ручка | 15.00 |
| products_cheap | 2 | Блокнот | 99.99 |
| products_medium | 3 | Наушники | 100.00 |
| products_medium | 4 | Клавиатура | 450.00 |
| products_medium | 5 | Монитор | 999.99 |
| products_expensive | 6 | Ноутбук | 1000.00 |
| products_expensive | 7 | Сервер | 25000.00 |

Видна та же логика полуинтервала: 99.99 — ещё `cheap`, ровно 100.00 — уже `medium`,
999.99 — ещё `medium`, ровно 1000.00 — уже `expensive`.

### Запрос по диапазону цены

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM products WHERE price >= 100 AND price < 500;
```

```
Seq Scan on products_medium products  (actual time=0.003..0.004 rows=2 loops=1)
  Filter: ((price >= '100'::numeric) AND (price < '500'::numeric))
  Rows Removed by Filter: 1
  Buffers: shared hit=1
Execution Time: 0.010 ms
```

**Какие партиции PostgreSQL должен просмотреть и почему?**

Только `products_medium`. Запрошенный диапазон `[100, 500)` целиком лежит внутри границ
этой партиции `[100, 1000)`. Партиция `products_cheap` содержит цены строго меньше 100,
`products_expensive` — от 1000 и выше, поэтому обе гарантированно не содержат подходящих
строк и исключаются на этапе планирования. Внутри партиции всё равно остаётся `Filter`,
потому что верхняя граница запроса (500) проходит по середине партиции: строка с ценой
999.99 попала в партицию, но не подходит под условие — это видно как `Rows Removed by Filter: 1`.

## Часть 4. LIST PARTITIONING

```sql
CREATE TABLE lab3.customers (
    id BIGINT NOT NULL, name TEXT NOT NULL, customer_type VARCHAR(30) NOT NULL
) PARTITION BY LIST (customer_type);

CREATE TABLE customers_b2c        PARTITION OF customers FOR VALUES IN ('B2C');
CREATE TABLE customers_b2b        PARTITION OF customers FOR VALUES IN ('B2B');
CREATE TABLE customers_enterprise PARTITION OF customers FOR VALUES IN ('Enterprise');
```

| partition_name | count |
|---|---|
| customers_b2c | 2 |
| customers_b2b | 2 |
| customers_enterprise | 1 |

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE customer_type = 'B2B';
```

```
Seq Scan on customers_b2b customers  (actual time=0.003..0.004 rows=2 loops=1)
  Filter: ((customer_type)::text = 'B2B'::text)
  Buffers: shared hit=1
Execution Time: 0.016 ms
```

- **Какая партиция используется:** только `customers_b2b`.
- **Почему PostgreSQL может не обращаться к другим:** из определения партиций следует, что
  значение `'B2B'` физически может находиться только в `customers_b2b` — остальные объявлены
  через `FOR VALUES IN ('B2C')` и `IN ('Enterprise')`. Планировщик доказывает это до выполнения
  и полностью исключает их из плана.
- **Чем этот сценарий отличается от RANGE:** в RANGE партиция задаётся интервалом, и условие
  запроса может пересекать несколько партиций частично — тогда останется `Filter` внутри
  партиции (как в части 3 со строкой 999.99). В LIST партиция задаётся точным перечнем
  значений, и условие равенства попадает ровно в одну партицию без остатка. LIST подходит
  для небольшого фиксированного набора категорий, RANGE — для непрерывных величин
  (даты, числа), где значений бесконечно много.

## Часть 5. LIST PARTITIONING: что делать с неизвестным значением?

Попытка вставить тип, для которого партиция не объявлена:

```sql
INSERT INTO customers VALUES (100, 'Test User', 'VIP');
```

```
ERROR:  no partition of relation "customers" found for row
DETAIL:  Partition key of the failing row contains (customer_type) = (VIP).
```

После создания DEFAULT-партиции та же вставка проходит:

```sql
CREATE TABLE customers_default PARTITION OF customers DEFAULT;
INSERT INTO customers VALUES (100, 'Test User', 'VIP');   -->  INSERT 0 1
```

| partition_name | id | name | customer_type |
|---|---|---|---|
| customers_default | 100 | Test User | VIP |

**1. Зачем нужна DEFAULT partition?** Она принимает все строки, не подошедшие ни под одну
объявленную партицию. Без неё любое новое значение ключа означает отказ на `INSERT`.

**2. Чем она полезна?** Это страховка от потери данных при появлении значений, которых
не было на момент проектирования: новый тип клиента, новая страна, опечатка в справочнике.
Вместо падения приложения строка сохраняется, и проблему можно разобрать позже, не теряя
запись. Для RANGE-партиционирования по дате DEFAULT играет ту же роль, что и job из части 10:
подстраховывает на случай, если нужная партиция не была создана вовремя.

**3. Какие проблемы могут возникнуть, если постоянно складывать новые значения в DEFAULT?**

- DEFAULT превращается в свалку и растёт без ограничений, теряя весь смысл разделения:
  по ней невозможен pruning, потому что PostgreSQL не знает, каких значений там нет.
- Любой запрос по ключу партиционирования вынужден просматривать DEFAULT в дополнение
  к «своей» партиции, потому что подходящая строка может лежать и там.
- Добавить новую партицию для значения, которое уже попало в DEFAULT, становится дорого:
  PostgreSQL обязан просканировать всю DEFAULT-партицию и убедиться, что в ней нет строк,
  которые должны были бы принадлежать новой партиции. На большой таблице это длительная
  блокировка.
- Проблема перестаёт быть заметной: данные молча накапливаются вместо того, чтобы вызвать
  ошибку и привлечь внимание. Поэтому DEFAULT стоит сочетать с мониторингом её наполнения.

## Часть 6. HASH PARTITIONING

```sql
CREATE TABLE lab3.user_events (
    id BIGINT NOT NULL, user_id BIGINT NOT NULL,
    event_type VARCHAR(50), created_at TIMESTAMP NOT NULL
) PARTITION BY HASH (user_id);

CREATE TABLE user_events_0 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE user_events_1 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE user_events_2 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE user_events_3 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

Загружено 400 000 строк со случайным `user_id` из 100 000 значений.

| partition_name | count | доля |
|---|---|---|
| user_events_0 | 100 576 | 25.14% |
| user_events_1 | 99 878 | 24.97% |
| user_events_2 | 99 827 | 24.96% |
| user_events_3 | 99 719 | 24.93% |

### Задание

**1. Насколько равномерно распределились данные?** Практически идеально: отклонение от
четверти не превышает 0.14 процентного пункта, разброс между самой большой и самой маленькой
партицией — 857 строк на 400 тысяч (0.2%). Хеш-функция PostgreSQL равномерно размазывает
значения по остаткам, и на большом количестве строк перекос исчезает.

**2. Почему HASH может быть полезен?** Когда у данных нет естественного диапазона или
категории, но таблицу всё равно нужно разбить на части: чтобы уменьшить размер отдельной
физической таблицы и её индексов, распределить нагрузку и конкуренцию за блокировки между
партициями, разложить партиции по разным табличным пространствам. Он также гарантирует,
что все строки одного пользователя лежат в одной партиции — это ускоряет запросы вида
`WHERE user_id = ?`, где pruning оставляет ровно одну партицию.

**3. Чем HASH отличается от RANGE?** В RANGE партицию определяет понятный человеку интервал
значений, партиции упорядочены, и их можно добавлять и отцеплять по мере движения времени.
В HASH принадлежность определяется остатком от хеша, порядка между партициями нет, их набор
фиксируется числом `MODULUS` при проектировании. Добавить пятую партицию к четырём нельзя
без перераспределения данных, тогда как в RANGE новая партиция добавляется одной командой.
Pruning в HASH работает только для условия равенства: `user_id = 123` сводится к одной
партиции, а `user_id BETWEEN 100 AND 200` — ни к одной, потому что соседние значения
попадают в разные партиции.

**4. Почему HASH плохо подходит для сценария «удалить данные старше 3 лет»?** Потому что
строки за любой период равномерно размазаны по всем партициям — в каждой лежат и свежие,
и трёхлетние записи. Удаление превращается в обычный `DELETE ... WHERE created_at < ...`
по всем партициям сразу: полное сканирование, распухание таблиц мёртвыми строками и долгий
`VACUUM`. При RANGE по дате та же задача решается мгновенно и без нагрузки:
`ALTER TABLE ... DETACH PARTITION` или `DROP TABLE` старой партиции — это операция над
метаданными, не зависящая от количества строк внутри.

## Часть 7. Выбор стратегии партиционирования

**Сценарий A.** Миллионы событий в день, через 3 года нужно быстро удалять данные старше
трёх лет. → **RANGE по дате** (по месяцам). Только эта стратегия превращает удаление старых
данных в `DROP TABLE`/`DETACH PARTITION` — операцию над метаданными, которая выполняется
мгновенно независимо от объёма, вместо `DELETE` на миллиарды строк с последующим VACUUM.

**Сценарий B.** Пользователи трёх типов (B2C, B2B, Enterprise), запросы фильтруют по типу.
→ **LIST по `customer_type`**. Набор значений мал, фиксирован и известен заранее, а фильтр
идёт по равенству — pruning оставит ровно одну партицию, как показано в части 4. Стоит сразу
добавить DEFAULT-партицию на случай появления четвёртого типа.

**Сценарий C.** Нужно равномерно распределить данные по нескольким физическим разделам
по `user_id`. → **HASH по `user_id`**. У идентификатора нет ни осмысленного диапазона,
ни категорий, а задача сформулирована именно как равномерное распределение — это ровно то,
что даёт хеш: в части 6 получилось 24.93–25.14% на партицию.

**Сценарий D.** Таблица заказов, аналитика почти всегда работает с `created_at BETWEEN ...`.
→ **RANGE по `created_at`**. Ключ партиционирования совпадает с колонкой, по которой идёт
фильтрация диапазоном, поэтому pruning отсечёт все партиции вне запрошенного периода —
именно этот эффект измерен в частях 2 и 12.

**Сценарий E.** Таблица платежей, разделение по странам (EE, LV, LT, FI, SE).
→ **LIST по коду страны**. Страна — это конечный перечень категориальных значений, запросы
к ней идут по равенству или `IN`. Дополнительный плюс: партиции по странам удобно разносить
по разным табличным пространствам и применять к ним разные политики хранения, что часто
требуется по регуляторным причинам.

## Часть 8. Партиционирование и индексы

```sql
CREATE INDEX idx_events_user_id ON lab3.events (user_id);
```

**На каком уровне существует индекс.** Команда, выполненная на родительской таблице, создаёт
не один объект, а иерархию: партиционированный индекс-«шаблон» на родителе и по одному
обычному физическому индексу на каждой партиции.

| relname | relkind | вид |
|---|---|---|
| `idx_events_user_id` | `I` | партиционированный (родительский) |
| `events_2026_09_09_user_id_idx` | `i` | обычный (на партиции) |
| `events_2026_09_10_user_id_idx` | `i` | обычный (на партиции) |
| `events_2026_09_11_user_id_idx` | `i` | обычный (на партиции) |

Родительский индекс данных не содержит и служит только для того, чтобы новые партиции
автоматически получали такой же индекс.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11' AND user_id = 12345;
```

```
Bitmap Heap Scan on events_2026_09_10 events  (actual time=0.019..0.019 rows=0 loops=1)
  Recheck Cond: (user_id = 12345)
  Filter: ((created_at >= '2026-09-10') AND (created_at < '2026-09-11'))
  Buffers: shared hit=3 read=2
  ->  Bitmap Index Scan on events_2026_09_10_user_id_idx  (actual time=0.018..0.018 rows=0 loops=1)
        Index Cond: (user_id = 12345)
Execution Time: 0.039 ms
```

**1. Какие партиции отфильтрованы через pruning?** `events_2026_09_09` и `events_2026_09_11`
исключены по условию на `created_at`, в плане осталась единственная партиция
`events_2026_09_10`.

**2. Используется ли индекс?** Да: `Bitmap Index Scan on events_2026_09_10_user_id_idx`
с `Index Cond: (user_id = 12345)`.

**3. На каком уровне существует индекс?** Физически — на уровне партиции. Запрос работает
с индексом конкретной партиции, а не с общим индексом всей таблицы. Родительский
`idx_events_user_id` в плане не фигурирует вообще.

**4. Почему комбинация partitioning + index эффективнее каждого механизма по отдельности?**

Они отсекают лишнюю работу на разных уровнях и по разным колонкам. Partition pruning
работает грубо и до выполнения: он выбрасывает целые физические таблицы по ключу
партиционирования, и цена этого — ноль, потому что решение принимается на этапе планирования.
Индекс работает тонко и внутри оставшихся данных: он находит конкретные строки по другой
колонке. Здесь это видно по числу буферов:

| Подход | Buffers | Что читается |
|---|---|---|
| Только partitioning (часть 2) | 932 | вся партиция за 10 сентября |
| Только индекс, без pruning (часть 9) | 73 | индексы всех трёх партиций |
| **Partitioning + index** | **5** | индекс одной партиции |

Сначала pruning сократил объём втрое (три партиции → одна), затем индекс внутри неё свёл
чтение к пяти буферам вместо 932. Дополнительный выигрыш: индекс партиции в три раза меньше
общего индекса, поэтому и дерево ниже, и в память он помещается легче.

## Часть 9. Когда партиционирование не помогает

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

**До создания индекса** — `Parallel Append` по всем трём партициям, `Buffers: shared hit=2805`,
`Rows Removed by Filter` на каждой партиции, Execution Time 8.653 мс.

```sql
CREATE INDEX idx_events_event_type ON lab3.events (event_type);
```

**После создания индекса:**

```
Aggregate  (actual time=7.894..7.894 rows=1 loops=1)
  Buffers: shared hit=5 read=68
  ->  Append  (actual time=0.020..6.041 rows=75054 loops=1)
     ->  Index Only Scan using events_2026_09_09_event_type_idx  (rows=25197)  Heap Fetches: 0
     ->  Index Only Scan using events_2026_09_10_event_type_idx  (rows=24824)  Heap Fetches: 15
     ->  Index Only Scan using events_2026_09_11_event_type_idx  (rows=25033)  Heap Fetches: 7
Execution Time: 7.938 ms
```

### Сравнение

| Метрика | Без индекса | С индексом |
|---|---|---|
| Партиций в плане | 3 из 3 | 3 из 3 |
| Тип доступа | Parallel Seq Scan | Index Only Scan |
| **Buffers** | **2805** | **73** |
| Execution Time | 8.653 мс | 7.938 мс |

**Почему partitioning сам по себе не решил проблему этого запроса?**

Потому что таблица разделена по `created_at`, а запрос фильтрует по `event_type`. Границы
партиций не содержат никакой информации о том, какие типы событий внутри них лежат, поэтому
доказать, что какая-то партиция не нужна, невозможно — приходится читать все три. Partitioning
уменьшил размер каждой отдельной таблицы, но суммарный объём чтения остался прежним.
Проблему решил индекс: он сократил чтение с 2805 буферов до 73, то есть в 38 раз.

Отдельно стоит отметить, что Execution Time при этом почти не изменился (8.65 → 7.94 мс).
Причина в том, что вариант без индекса выполнялся в три параллельных процесса, а вариант
с индексом — в один, и все данные уже находились в кэше. На объёме, который не помещается
в память, разница в 38 раз по количеству читаемых блоков превратилась бы и в разницу по
времени: это ровно тот эффект, который измерен в лабораторной №2.

**Вывод: партиционирование отвечает на одну проблему, а индекс — на другую.**

Партиционирование отвечает на вопрос «какие физические куски таблицы можно вообще не трогать»
и работает только по ключу партиционирования. Индекс отвечает на вопрос «как быстро найти
нужные строки внутри того, что осталось» и работает по своей колонке. Заменить одно другим
нельзя: если бы мы партиционировали по `event_type`, этот запрос стал бы быстрым, но запрос
по диапазону дат из части 2 потерял бы pruning и удаление старых данных перестало бы быть
операцией над метаданными.

## Часть 10. Автоматическое создание партиций

Автоматизация построена на **pg_cron** — расширении PostgreSQL, которое выполняет
SQL-задачи по расписанию прямо внутри сервера базы данных. Подробное описание устройства,
настройки и схема работы — в отдельном документе [docs/lab-03-pg-cron.md](docs/lab-03-pg-cron.md).

### Подготовка: PostgreSQL с pg_cron

В официальном образе `postgres:16-alpine` расширения pg_cron нет, поэтому оно собрано
из исходников (версия v1.6.4) на том же базовом образе — `deploy/postgres/Dockerfile`.
Базовый образ сохранён сознательно: Alpine использует musl, а Debian-образы — glibc,
у которых разные правила сортировки строк. Том с данными создан под musl, и при смене
libc текстовые индексы стали бы некорректными. После пересоздания контейнера все объёмы
данных совпали с исходными.

pg_cron загружается при старте сервера, поэтому параметры переданы в командной строке
`postgres` в `docker-compose.yml`:

```
shared_preload_libraries=pg_cron        -- загрузить планировщик вместе с сервером
cron.database_name=booking_service      -- база, где хранится расписание
cron.use_background_workers=on          -- выполнять задачи фоновыми процессами сервера
cron.timezone=UTC                       -- часовой пояс расписания
max_worker_processes=20                 -- пул фоновых процессов
```

Результат — в логе сервера `LOG:  pg_cron scheduler started`, а в базе:

```sql
SHOW shared_preload_libraries;   -- pg_cron
SELECT name, default_version FROM pg_available_extensions WHERE name = 'pg_cron';  -- pg_cron | 1.6
```

### CreatePartitionsJob

pg_cron выполняет только SQL, поэтому job реализован как функция PL/pgSQL
`lab3.create_missing_partitions` в файле `deploy/postgres/initdb/10-partitions-pg-cron.sql`.
Алгоритм соответствует схеме из задания:

```
определить сегодняшнюю дату      (now() AT TIME ZONE 'UTC')::date
        ↓
определить требуемый горизонт    lab3.required_partitions: сегодня + 3 периода
        ↓
получить существующие партиции   lab3.existing_partitions: системный каталог pg_inherits
        ↓
найти отсутствующие              требуемые минус существующие
        ↓
создать их                       EXECUTE format('CREATE TABLE IF NOT EXISTS %I.%I
                                                 PARTITION OF %I.%I FOR VALUES FROM (%L) TO (%L)')
```

Функция параметризована и одинаково работает с дневными и месячными партициями:

```sql
SELECT report FROM lab3.create_missing_partitions('lab3', 'events', 'day', 3);
```

### Требования и как они выполнены

| Требование | Реализация |
|---|---|
| Создавать недостающие партиции | разность между требуемым набором и системным каталогом `pg_inherits` |
| Не создавать уже существующие | имя партиции вычисляется детерминированно из даты и сверяется с каталогом |
| Быть безопасной при повторном запуске | сверка с каталогом плюс `CREATE TABLE IF NOT EXISTS`; вся функция выполняется в одной транзакции |
| Логировать результат работы | текстовый отчёт в формате методички и запись в таблицу `lab3.partition_job_log` |

Имена и значения подставляются через `format('%I', ...)` и `format('%L', ...)`: PostgreSQL сам
экранирует идентификаторы и литералы, поэтому SQL-инъекция через имя таблицы невозможна.
Дополнительно есть параметр `p_dry_run`, показывающий, что было бы создано, без изменений.

### Реальный вывод job

```
2026-09-13 21:23:42 UTC

Partition job started.

Existing partitions: 7
Required partitions: 4
Missing partitions: 1

Creating:
events_2026_09_16

Partition created successfully: events_2026_09_16 [2026-09-16 .. 2026-09-17)

Partition job finished.
```

Требуемых партиций 4, а не 3, потому что горизонт «3 дня вперёд» означает сегодняшнюю
партицию плюс три будущих: для даты 13 сентября (UTC) это партиции с 13 по 16 сентября.

### Проверка идемпотентности — повторный запуск сразу после первого

```
2026-09-13 21:23:43 UTC

Partition job started.

Existing partitions: 8
Required partitions: 4
Missing partitions: 0

Nothing to create, all required partitions already exist.

Partition job finished.
```

Ничего не создаётся и ошибок не возникает — job безопасно запускать хоть каждую минуту.

### Постановка в расписание

Задачи регистрируются в pg_cron в том же SQL-файле:

```sql
SELECT cron.schedule(
    'lab3-events-create-partitions',
    '0 1 * * *',
    $$SELECT lab3.create_missing_partitions('lab3', 'events', 'day', 3)$$
);
```

Расписание хранится в таблице `cron.job` внутри базы:

```
 jobid |             jobname             | schedule  |                                  command
-------+---------------------------------+-----------+----------------------------------------------------------------------------
     1 | lab3-events-create-partitions   | 0 1 * * * | SELECT lab3.create_missing_partitions('lab3', 'events', 'day', 3)
     2 | lab3-events-check-partitions    | 5 1 * * * | SELECT lab3.check_partitions('lab3', 'events', 'day', 3)
     3 | lab3-bookings-create-partitions | 0 1 * * * | SELECT lab3.create_missing_partitions('lab3', 'bookings_partitioned', 'month', 3)
     4 | lab3-bookings-check-partitions  | 5 1 * * * | SELECT lab3.check_partitions('lab3', 'bookings_partitioned', 'month', 3)
```

Каждую ночь в **01:00 UTC** pg_cron создаёт недостающие партиции, в **01:05 UTC** проверяет,
что они на месте. `cron.schedule` с тем же именем обновляет задачу, а не создаёт дубль:
скрипт выполнен дважды, задач по-прежнему четыре с теми же `jobid`.

Разрыв в 5 минут между задачами обязателен. Разные задачи pg_cron стартуют в одну минуту
параллельно, в отдельных фоновых процессах, и проверка могла бы успеть раньше, чем job
создаст партицию, выдав ложный CRITICAL.

**Подтверждение, что расписание работает.** Чтобы не ждать ночи, задача создания была
временно переключена на «каждую минуту» (`SELECT cron.alter_job(1, schedule := '* * * * *')`).
pg_cron сам запустил её и записал результат в `cron.job_run_details`:

```
 runid | jobid |  status   | return_message |         start_utc
-------+-------+-----------+----------------+----------------------------
     3 |     1 | succeeded | SELECT 1       | 2026-09-13 21:17:00.003912
```

и в журнал `lab3.partition_job_log`:

```
 id |  job   | status  | existing | required |                     created
----+--------+---------+----------+----------+--------------------------------------------------
  3 | create | CREATED |        7 |        4 | {"events_2026_09_16 [2026-09-16 .. 2026-09-17)"}
```

Партиция `events_2026_09_16` появилась без ручного запуска какой-либо команды.

Для ручного запуска той же функции остаётся management-команда
`python manage.py create_partitions` — она не содержит своей логики, а вызывает
`lab3.create_missing_partitions`. Поэтому ручной и плановый запуск выполняют один и тот же код.

## Часть 11. Production-сценарий: ночной job сломался

PartitionHealthCheck реализован как функция `lab3.check_partitions` в том же SQL-файле
и запускается pg_cron в 01:05 UTC. Функция вычисляет тот же требуемый набор партиций, что
и job, сверяет его с каталогом, возвращает статус `OK` или `CRITICAL` и построчный отчёт.

```sql
SELECT status, report FROM lab3.check_partitions('lab3', 'events', 'day', 3);
```

Ручной запуск — `python manage.py check_partitions`; команда вызывает эту же функцию
и возвращает код 1 при CRITICAL, чтобы проблему видел и внешний мониторинг.

### Шаг 1. Искусственный сбой

```sql
DROP TABLE lab3.events_2026_09_16;
```

### Шаг 2. Проверка обнаруживает проблему

Вывод функции проверки:

```
PartitionHealthCheck: lab3.events
Checked at: 2026-09-13 21:23:42 UTC

  ✓ events_2026_09_13
  ✓ events_2026_09_14
  ✓ events_2026_09_15
  ✗ events_2026_09_16

Результат проверки: CRITICAL (отсутствует партиций: 1)
Уведомление поставлено в очередь: lab3.partition_alerts id=5
```

### 11.1. Отправка уведомления

Канал — **email**. Сама база отправлять письма не умеет, поэтому доставка устроена так:

```
pg_cron (01:05) → lab3.check_partitions()
                    ├─ INSERT в таблицу-очередь lab3.partition_alerts
                    └─ pg_notify('partition_alert', id)
                                  │  сигнал уходит в момент фиксации транзакции
                                  ▼
          сервис partition-alerts: python manage.py partition_alert_listener
                    ├─ LISTEN partition_alert
                    ├─ берёт неотправленные записи (FOR UPDATE SKIP LOCKED)
                    ├─ send_mail() через email-бэкенд Django
                    └─ UPDATE ... SET sent_at = now()
```

Таблица — источник истины, сигнал только будит слушателя. Сигнал NOTIFY не сохраняется:
если слушатель перезапускался в момент проверки, сигнал пропал бы. Поэтому при запуске,
после переподключения и раз в минуту слушатель отправляет всё, что лежит в очереди
с пустым `sent_at`. Это проверено: при остановленном слушателе уведомление осталось
в очереди и было отправлено сразу после его запуска.

Настройки почты вынесены в переменные окружения (`booking_service/settings.py`).
По умолчанию используется файловый бэкенд, складывающий письма в каталог `alerts/`, —
это позволяет увидеть факт отправки и содержимое без внешнего SMTP. Для реальной рассылки
достаточно задать `DJANGO_EMAIL_BACKEND`, `EMAIL_HOST`, `EMAIL_HOST_USER`,
`EMAIL_HOST_PASSWORD` и `PARTITION_ALERT_RECIPIENTS` — код при этом не меняется.

Письмо, созданное проверкой, которую запустил pg_cron
(`alerts/20260913-211500-281473708816576.log`):

```

From: partition-monitor@booking-service.local
To: dba@booking-service.local

🚨 Partition alert

events_2026_09_16

```

Очередь уведомлений показывает, что письмо ушло через 11 миллисекунд после проверки:

```
----+----------+-------------+----------------------------+----------------------------
```

### 11.2. Проверка того, что alert действительно работает

Сценарий из задания выполнен полностью силами pg_cron, без ручного запуска проверки или job.
Задачи временно переключались на расписание «каждую минуту» через `cron.alter_job`:

1. создана партиция на 3 дня вперёд (часть 10);
2. удалена одна из будущих партиций — `events_2026_09_16`;
3. pg_cron в 21:15:00 запустил `PartitionHealthCheck`;
4. проверка обнаружила проблему и записала CRITICAL;
5. слушатель получил сигнал и отправил письмо — файл появился в `alerts/`.

Ключевой момент: проблема обнаружена **до** того, как приложение попыталось вставить строку
за 16 сентября и получило `no partition of relation "events" found for row`.

## Часть 12. Партиционирование собственной базы данных

### Шаг 1. Выбор таблицы

**`bookings`** — центральная растущая сущность сервиса бронирования, 300 004 строки,
диапазон `created_at` с 2024-09-10 по 2026-09-10.

**Важное ограничение.** Партиционировать существующую `public.bookings` «на месте»
нельзя без ломки схемы: PostgreSQL требует, чтобы ключ партиционирования входил в первичный
ключ, то есть `PRIMARY KEY (id_booking)` пришлось бы заменить на `(id_booking, created_at)`.
Уникального ограничения на одном `id_booking` при этом не останется, а на него ссылаются
два внешних ключа:

```
payments        | FOREIGN KEY (id_booking) REFERENCES bookings(id_booking)
bookingservices | FOREIGN KEY (id_booking) REFERENCES bookings(id_booking)
```

Оба FK пришлось бы удалить, а схема БД разошлась бы с Django-моделями и миграциями.
Поэтому эксперимент выполнен на полной партиционированной копии
`lab3.bookings_partitioned`, куда скопированы все 300 004 строки. Рабочая таблица сервиса,
её внешние ключи и миграции не затронуты. Это и есть первый практический вывод: **перевод
существующей таблицы на партиционирование — не команда, а миграция данных со сменой
первичного ключа и перестройкой внешних ключей.**

### Шаг 2. Выбор ключа

**`created_at`.** Это единственная колонка, которая монотонно растёт вместе с таблицей,
никогда не обновляется после вставки и участвует в фильтрации почти всех списочных запросов
API (`?created_from`, `?created_to`, сортировка по умолчанию `ORDER BY created_at DESC`).
Кандидат `status` отпадает: значений всего пять, они распределены равномерно по 20%,
а главное — статус брони **меняется** со временем (`pending → confirmed → checked_in →
checked_out`), а изменение ключа партиционирования означает физический перенос строки
между партициями. Кандидат `id_guest` не подходит, потому что не даёт ничего для удаления
старых данных и не связан с диапазонными запросами.

### Шаг 3. Выбор стратегии

**RANGE, по месяцам.** RANGE — потому что `created_at` непрерывен и запросы к нему идут
диапазоном. Месяц как размер партиции выбран из темпа роста: сервис даёт около 150 тысяч
броней в год, то есть примерно 12 тысяч строк и около 2 МБ на партицию — достаточно крупно,
чтобы не плодить тысячи объектов, и достаточно мелко, чтобы отцеплять данные помесячно.
Дневные партиции при таком темпе дали бы 365 почти пустых таблиц в год и заметно утяжелили
бы планирование (эффект виден ниже в запросах 2 и 3).

### Шаг 4. Объяснение выбора

- **Почему эта таблица?** Она единственная в схеме растёт линейно и неограниченно: строки
  только добавляются, отменённые брони не удаляются, а помечаются `status = 'cancelled'`.
  Остальные таблицы — справочники (`rooms`, `roomtypes`, `services`) или насыщающиеся
  (`guests`).
- **Почему этот ключ?** `created_at` не меняется после вставки, монотонно растёт, участвует
  в фильтрах и сортировке по умолчанию и позволяет отцеплять старые периоды одной операцией.
- **Почему эта стратегия?** Только RANGE по дате превращает архивацию старых броней
  в `DETACH PARTITION` вместо `DELETE` на сотни тысяч строк.
- **Какие запросы должны получить пользу от pruning?** Все, где есть условие на `created_at`:
  выборка списка за период (`GET /api/bookings?created_from=&created_to=`), отчёты за месяц,
  подсчёт `COUNT(*)` за диапазон. Запросы без условия на дату (поиск по `id_guest`, фильтр
  по `status`) выигрыша не получат — это подтверждено измерениями ниже.

### Шаг 5. Создание партиций

Создано **28 месячных партиций**, покрывающих весь диапазон данных и три месяца вперёд —
с `bookings_partitioned_2024_09` по `bookings_partitioned_2026_12`:

```sql
CREATE TABLE lab3.bookings_partitioned (
```

### Шаг 6. Проверка реальных запросов API

Взяты три реальных запроса сервиса из `main/repositories/booking_repository.py`. Каждый
выполнен с `EXPLAIN (ANALYZE, BUFFERS)` и на партиционированной копии, и на обычной
`public.bookings` с тем же набором данных.

**Запрос 1 — `GET /api/bookings?created_from=2026-07-01&created_to=2026-08-01`** (список за период):

```sql

WHERE b.created_at >= '2026-07-01' AND b.created_at < '2026-08-01'
ORDER BY b.created_at DESC LIMIT 20;
```

```

        on bookings_partitioned_2026_07 b   (actual time=0.013..0.069 rows=20 loops=1)
```

**Partition pruning сработал: в плане ровно одна партиция из 28.**

**Запрос 2 — `GET /api/guests/29604/bookings`** (поиск по внешнему ключу):

В плане `Append` по **всем 28 партициям** — условия на `created_at` нет, исключить нечего.

**Запрос 3 — `GET /api/bookings?status=confirmed`** (фильтр + сортировка + LIMIT):

В плане тоже **все 28 партиций**, но это `Append` из упорядоченных `Index Scan`, и почти все
ветки помечены `(never executed)`: `LIMIT 20` набирается из самой свежей партиции, до
остальных выполнение не доходит.

| Запрос | Партиций в плане | Buffers (партиц.) | Время (партиц.) | Buffers (обычная) | Время (обычная) | Pruning |
|---|---|---|---|---|---|---|
| 1. Список за период | **1 из 28** | **22** | 0.073 мс | 23 | 0.104 мс | **да** |

Пользу от партиционирования получил только запрос 1 — единственный, где фильтр наложен
на ключ партиционирования. Запрос 2 на партиционированной таблице стал **втрое дороже**
(72 буфера против 25): вместо одного обращения к общему индексу по `id_guest` планировщику
приходится опрашивать 28 отдельных индексов, по одному на партицию. Запрос 3 формально
тоже читает все партиции, но благодаря `LIMIT` и упорядоченному `Append` реально почти
не деградирует — цену он платит в основном на этапе планирования.

На нынешних 300 тысячах строк партиционирование не окупается: выигрыш запроса 1 измеряется
сотыми долями миллисекунды, а запрос 2 проигрывает. Смысл оно приобретёт, когда таблица
вырастет до миллионов строк и появится задача архивации старых периодов — тогда `DETACH
PARTITION` вместо `DELETE` будет решающим аргументом. Это прямое продолжение вывода
лабораторной №2: инструмент нужно выбирать под форму запроса и под объём, а не «на всякий
случай».

### Шаг 7. Автоматизация создания партиций

Автоматизация та же, что в части 10, — pg_cron вызывает функцию
`lab3.create_missing_partitions`, но с месячной гранулярностью. Задача зарегистрирована

```sql
SELECT cron.schedule(
    'lab3-bookings-create-partitions',
    '0 1 * * *',
```

горизонт в 3 месяца даёт большой запас: даже если job не отработает несколько недель подряд,
вставки не начнут падать.

## Контрольные вопросы

**1. Что такое partitioning?** Разделение одной логической таблицы на несколько физических
таблиц-партиций по значению ключа. Для приложения таблица остаётся одной, а PostgreSQL
внутри работает с отдельными таблицами, каждая со своими файлами, индексами и статистикой.

**2. Чем partitioning отличается от индекса?** Индекс — дополнительная структура, которая
помогает быстро найти строки, не меняя хранение самой таблицы. Партиционирование меняет
именно физическое хранение и позволяет целиком исключить ненужные куски данных ещё до
выполнения запроса. Индекс работает по своей колонке, pruning — только по ключу
партиционирования; в части 9 видно, что одно не заменяет другое.

**3. Какие стратегии partitioning поддерживает PostgreSQL?** RANGE (диапазоны значений),
LIST (перечень значений), HASH (остаток от хеша). Партиции можно вкладывать друг в друга,
создавая многоуровневое разбиение, и для RANGE и LIST существует DEFAULT-партиция.

**4. Когда использовать RANGE?** Когда ключ непрерывен и запросы идут диапазоном: даты,
числовые интервалы, суммы. Главный сценарий — данные, живущие по времени, где нужны
и выборки за период, и быстрое удаление старых периодов.

**5. Когда использовать LIST?** Когда ключ — небольшой фиксированный набор категорий
(тип клиента, страна, регион) и запросы фильтруют по равенству или `IN`.

**6. Когда использовать HASH?** Когда у ключа нет ни осмысленного диапазона, ни категорий,
а задача — равномерно распределить данные, чтобы уменьшить размер отдельных таблиц и снизить
конкуренцию. Например, разбиение по `user_id`.

**7. Как выбрать partition key?** По тому, как читаются и удаляются данные. Ключ должен
участвовать в условиях частых запросов (иначе pruning не сработает), не меняться после
вставки (иначе строка будет физически переезжать между партициями) и давать партиции
сопоставимого размера. В части 12 по этим критериям был выбран `created_at`, а `status`
отклонён именно потому, что меняется в течение жизни брони.

**8. Что такое partition pruning?** Исключение партиций, которые заведомо не содержат
подходящих строк, на основании их границ. Видно в плане по тому, что часть партиций
вообще не появляется: в части 2 вместо `Append` по трём партициям остался `Seq Scan`
по одной, а число буферов упало с 2805 до 932.

**9. Почему pruning может не сработать?** Если условие наложено не на ключ партиционирования
(часть 2: фильтр по `event_type` при разбиении по `created_at`), если условия по ключу нет
вообще (часть 12, запросы 2 и 3), если к ключу применена функция, мешающая сопоставить
значение с границами, или если значение ключа становится известно только во время выполнения.
В последнем случае помогает runtime pruning, но он работает не всегда.

**10. Можно ли использовать индексы вместе с partitioning?** Да, и это обычная практика.
`CREATE INDEX` на родительской таблице создаёт партиционированный индекс-шаблон
(`relkind = 'I'`) и по обычному индексу на каждой партиции (`relkind = 'i'`); новые партиции
получают такой индекс автоматически. В части 8 связка pruning + индекс дала 5 буферов против
932 у одного pruning и 73 у одного индекса.

**11. Что произойдёт, если подходящей партиции нет?** Вставка завершится ошибкой
`no partition of relation "..." found for row`. Если объявлена DEFAULT-партиция, строка
попадёт в неё; для RANGE по дате без DEFAULT это означает остановку записи в таблицу.

**12. Зачем создавать будущие партиции заранее?** Потому что партиция нужна в момент
вставки, а не в момент, когда о ней вспомнят. Данные за завтрашний день начнут приходить
ровно в полночь, и если партиции нет, приложение начнёт падать на `INSERT`. Запас
в несколько периодов даёт время заметить и починить сбой самого механизма создания.

**13. Почему создание партиций должно быть автоматизировано?** Потому что это регулярная
операция, привязанная к календарю, а не к релизам. Ручное создание рано или поздно будет
пропущено — в отпуске, на праздниках, при смене дежурного, — и отказ произойдёт в
продуктивной системе. Автоматизация к тому же делает процесс идемпотентным и проверяемым.
В этой работе её выполняет pg_cron: расписание хранится внутри базы в `cron.job`, а каждый
запуск фиксируется в `cron.job_run_details`, поэтому проверить, отработал ли job ночью,
можно обычным `SELECT`.

**14. Чем логирование ошибки отличается от alerting?** Лог пассивен: он фиксирует событие,
но его нужно пойти и прочитать. Alert активен: он сам находит человека по выбранному каналу.
Проблема с партициями не проявляется до первой неудачной вставки, поэтому строки в логе
недостаточно — к моменту, когда её заметят, приложение уже будет падать.

**15. Что такое recovery alert?** Уведомление о том, что ранее сообщённая проблема устранена
и система вернулась в нормальное состояние. Без него получатель видит только сообщение
о сбое и не знает, закрыт ли инцидент. В части 11 это письмо `[OK] Partition check recovered`,
которое отправляется при переходе CRITICAL → OK.

**16. Почему нельзя бесконечно отправлять одинаковый alert?** Повторяющиеся уведомления
обесценивают канал: их начинают игнорировать и вместе с ними пропускают новые, действительно
важные сообщения. Поэтому уведомление отправляется только при смене состояния, а пока
проблема держится, повторы подавляются — измерено в 11.4: две подряд проверки pg_cron
в статусе CRITICAL (21:15 и 21:16) дали ровно одно письмо.

**17. Всегда ли partitioning ускоряет запросы?** Нет, и в этой работе есть прямое
подтверждение. Запрос 2 части 12 (поиск по `id_guest`) на партиционированной таблице стал
втрое дороже: 72 буфера против 25, потому что без условия на ключ партиционирования
приходится опрашивать индексы всех 28 партиций вместо одного общего. Партиционирование
ускоряет запросы по ключу разбиения и замедляет остальные, а также удорожает планирование.

**18. Какие проблемы возникают при неправильном выборе размера партиций?** Слишком мелкие
партиции дают их огромное количество: растёт время планирования (планировщик рассматривает
каждую), раздувается системный каталог, любой запрос без pruning опрашивает сотни объектов.
Слишком крупные партиции лишают партиционирование смысла: pruning отсекает мало, отдельная
партиция остаётся неподъёмной, а удаление старых данных снова требует `DELETE` вместо
`DROP`. Ориентир — партиция, соизмеримая с типичным диапазоном запроса и с единицей
архивации; в части 12 по темпу роста сервиса это месяц, а не день.
