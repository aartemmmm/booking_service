## 1. Выбор данных для шардирования

### 1. Какую сущность вы выбрали?

**Бронирования — таблица `bookings`.** Это единственная сущность сервиса, которая растёт
неограниченно: строки только добавляются, отменённые брони не удаляются, а получают
`status = 'cancelled'`. Остальные таблицы — справочники (`rooms`, `roomtypes`, `services`)
или растут медленно (`guests`). Та же сущность была выбрана как растущая в лабораторных 1–4.

### 2. Какое поле используется как shard key?

**`id_guest`** — идентификатор гостя, которому принадлежит бронь.

### 3. Почему выбран именно этот ключ?

- **Бронь естественно «принадлежит» гостю.** Все брони одного гостя попадают на один шард,
  поэтому запрос «брони гостя» идёт ровно в один PostgreSQL, а не во все три.
- **Много разных значений.** В данных 49 890 разных гостей. Чем больше значений у ключа,
  тем мельче единица, которую router раскладывает по шардам, и тем ровнее распределение.
- **Ни один гость не доминирует.** В среднем у гостя 6 броней, максимум 18. Самый активный
  гость — это 0.006% данных, так что «горячий ключ» не перегрузит шард.
- **Ключ известен в момент записи.** `id_guest` обязателен в теле `POST /api/bookings`,
  поэтому router может выбрать шард до вставки.

Отклонённые варианты:

| Ключ | Почему не подошёл |
|---|---|
| `id_room` | всего 305 значений, на комнату ~1 000 броней — грубое распределение, и одна комната переезжает сразу со всеми бронями. Плюс был бы в том, что проверка занятости комнаты осталась бы внутри одного шарда |
| `id_booking` | распределение идеальное, но брони одного гостя разлетелись бы по всем шардам, и любой список пришлось бы собирать со всех |
| `status` | 5 значений, и статус меняется в течение жизни брони — запись пришлось бы переносить |
| `created_at` | все новые брони попадали бы на один «горячий» шард |

### 4. Насколько равномерно он будет распределять данные?

Ожидание — **очень равномерно**. Ключей много (49 890), самый крупный ключ ничтожно мал,
а хеш перемешивает соседние `id_guest` и отправляет их на разные шарды. Для такого числа
ключей отклонение от идеальной трети должно быть порядка одного процента. Измерение
(часть 4) это подтвердило: **±0.57%**.

Оговорка: данные сгенерированы, и гости в них одинаково активны. В реальном отеле был бы
перекос — например, корпоративный клиент с тысячами броней. Такой ключ целиком лёг бы
на один шард.

### 5. Какие запросы сервиса используют этот ключ?

| Запрос | Использует `id_guest` | Сколько шардов затронет |
|---|---|---|
| `GET /api/guests/{id}/bookings` — брони гостя | да, фильтр `b.id_guest = ?` | **один** |
| `GET /api/bookings?guest_id=...` | да | **один** |
| `POST /api/bookings` — создание брони | да, `id_guest` в теле запроса | **один** |
| `PUT /api/bookings/{id}` — изменение | да, но может сменить гостя | один или **два** (перенос) |
| `GET /api/bookings/{id}` — карточка брони | нет, ищется по `id_booking` | **все** |
| `GET /api/bookings` — общий список с `ORDER BY created_at LIMIT` | нет | **все**, затем слияние |
| проверка занятости комнаты (`find_overlapping`) | нет, по `id_room` | **все** |
| `GET /api/rooms/{id}/bookings`, отчёты | нет | **все** |

Выбор ключа — это решение о том, какие запросы станут дешёвыми. Здесь дешёвыми становятся
запросы «по гостю», а запросы по комнате и общие списки превращаются в обращение ко всем
шардам. Отдельно стоит `PUT`: `update_booking` умеет менять `id_guest`, и при смене гостя
бронь пришлось бы физически перенести на другой шард.

## 3. Реализация простого Router

### Хеш-функция

[main/sharding/router.py:21](../main/sharding/router.py#L21)

```python
def stable_hash(value):
    digest = hashlib.md5(str(value).encode('utf-8')).digest()
    return int.from_bytes(digest[:8], 'big')
```

Хеш — первые 8 байт MD5 как 64-битное число. Встроенный `hash()` Python не подходит, и это
проверено:

```
hash(101)   = 101
hash("101") = -5560178762853630881   ← при следующем запуске Python будет другое число
```

- Для строк `hash()` меняется при каждом запуске интерпретатора (защита `PYTHONHASHSEED`).
  Два процесса backend отправляли бы одну и ту же бронь на разные шарды.
- Для чисел `hash(101) == 101`: «хеш» — это сам ключ, и распределение зависело бы от того,
  в каком порядке сервис выдаёт id гостям.

MD5 здесь используется не для безопасности, а как быстрая детерминированная функция
перемешивания: одно и то же значение на любой машине и в любом процессе даёт одно число.

### Router `hash(key) % N`

[main/sharding/router.py:34–49](../main/sharding/router.py#L34-L49)

```python
class ModuloRouter:
    """shard = hash(key) % N, где N — число шардов."""

    def __init__(self, shards):
        self.shards = list(shards)

    def shard_index(self, key):
        return stable_hash(key) % len(self.shards)

    def shard_for(self, key):
        return self.shards[self.shard_index(key)]
```

Router, которым пользуется сервис, — [main/sharding/\_\_init\_\_.py:14](../main/sharding/__init__.py#L14):

```python
def booking_router():
    return ModuloRouter(settings.BOOKING_SHARDS)
```

Router возвращает **имя подключения** (`'shard_1'`), а обращение к конкретному PostgreSQL
выполняет репозиторий [main/repositories/sharded_booking_repository.py](../main/repositories/sharded_booking_repository.py):

```python
def list_bookings_of_guest(guest_id):

    with connections[shard].cursor() as cursor:      # только этот PostgreSQL

```


### Вывод

- **Распределение очень равномерное.** Отклонения от идеальной трети — от −0.52% до +0.57%,
  самый большой шард больше самого маленького всего на 1.1%.
- **Заметного дисбаланса нет.** Разброс в тысячу броней на сто тысяч — случайный шум хеширования
  по 49 890 ключам, а не систематический перекос.
- **Может ли дисбаланс стать проблемой? Да, в двух случаях.** Во-первых, при горячих ключах:
  крупный корпоративный гость целиком лежит на одном шарде, и хеш этого не исправит.
  Во-вторых, равенство числа строк не означает равенства нагрузки: если на одном шарде окажутся
  самые активные гости, он будет получать больше запросов. Дисбаланс опасен тем, что система
  упирается в самый загруженный шард — именно он первым исчерпает диск или процессор,
  и именно его придётся разгружать переносом данных.

## 5. Что произойдёт при добавлении нового shard?

Для тех же 300 004 броней, которые лежат на шардах, вычислено, куда router отправил бы каждую
запись после перехода `hash(key) % 3` → `hash(key) % 4`:

```
python manage.py shard_bookings rebalance
```

```
Всего записей:     300 004
Новый shard:       shard_3

Изменили shard:    225 576   (75.19%)
Не изменили:        74 428   (24.81%)

Гостей сменили шард: 37 493 из 49 890
```

Куда уходят переехавшие записи:

| Направление | Записей |
|---|---|
| в новый `shard_3` | 75 203 |
| **между старыми шардами** `shard_0/1/2` | **150 373** |

Распределение после перехода — идеальное, по ~25% на каждом:

```
shard_0 74966 (24.99%)   shard_1 75255 (25.08%)   shard_2 74580 (24.86%)   shard_3 75203 (25.07%)
```

**Процент переносимых данных, посчитанный самостоятельно.** Запись остаётся на месте, только
если `h mod 3 = h mod 4`. Числа 3 и 4 взаимно просты, поэтому пара остатков `(h mod 3, h mod 4)`
однозначно определяется остатком `h mod 12`, и совпадают остатки ровно для
`h mod 12 ∈ {0, 1, 2}` — это 3 варианта из 12. Остаётся 3/12 = **25%**, переезжает **75%**.
Измерено **75.19%** — совпадает с расчётом с точностью до случайного шума.

### Вывод

Добавление одного PostgreSQL приводит к переносу трёх четвертей данных, потому что формула
`hash % N` зависит от `N` целиком: при изменении делителя меняется остаток почти у каждого
ключа, а не только у тех, которым «положено» уйти на новый шард. Новому шарду нужно всего
25% данных, но вместе с ними 150 тысяч броней — вдвое больше — бессмысленно перетасовываются
между тремя старыми шардами. На практике это значит, что добавление сервера превращается
в перемещение почти всей базы: долгий перенос, нагрузка на все узлы сразу и период, когда
router должен понимать и старое, и новое расположение.

## 6. Реализация Consistent Hashing

### Принцип

```
hash(shard_key)
      ↓
точка на кольце [0, 2^64)
      ↓
первая точка шарда по часовой стрелке — это и есть шард записи
```

Кольцо — это все возможные значения 64-битного хеша, у которых конец соединён с началом.
На кольцо ставятся точки шардов: позиция точки — `hash("shard_0#0")`, `hash("shard_1#0")` и т. д.
Ключ получает позицию `hash(id_guest)` и идёт по часовой стрелке до ближайшей точки шарда.

### Код

[main/sharding/router.py:52–96](../main/sharding/router.py#L52-L96)

```python
class ConsistentHashRouter:
    def __init__(self, shards, vnodes=1):
        points = sorted(
            (stable_hash(f'{shard}#{number}'), shard)
            for shard in self.shards
            for number in range(vnodes)
        )
        self._positions = [position for position, _ in points]
        self._owners = [shard for _, shard in points]

    def shard_for(self, key):
        position = stable_hash(key)
        index = bisect.bisect_right(self._positions, position)   # первая точка после ключа
        if index == len(self._positions):
            index = 0                                            # кольцо замыкается
        return self._owners[index]
```

- Позиции точек отсортированы, поэтому ближайшая точка по часовой стрелке ищется двоичным
  поиском (`bisect`), а не перебором.
- Если ключ стоит после последней точки, он принадлежит самой первой — так кольцо замыкается.
- `vnodes=1` — **базовое кольцо**: одна точка на шард. Параметр `vnodes` позволяет поставить
  каждому шарду несколько точек (virtual nodes). Он используется только для сравнения в части 7.

### Как выглядит кольцо из трёх шардов

Реальные позиции точек в процентах от длины кольца (100% замыкается на 0%):

```
кольцо:   0% ──────────────── 44.4% ──── 51.3% ─────────── 73.4% ──────────── 100% = 0%
точки:                        shard_0    shard_2           shard_1
```

Каждый шард владеет дугой от предыдущей точки до своей:

| Дуга | Владелец | Доля кольца |
|---|---|---|
| от 73.4% через 100% = 0% до 44.4% | `shard_0` | **71.0%** |
| от 44.4% до 51.3% | `shard_2` | **7.0%** |
| от 51.3% до 73.4% | `shard_1` | **22.0%** |

Три случайные точки поделили кольцо на **71.0% / 22.0% / 7.0%** — базовое кольцо почти никогда
не делит его поровну. После добавления `shard_3` его точка встала на **13.3%**, внутрь дуги
`shard_0`, и забрала отрезок от 73.4% до 13.3% — **40.0%** кольца.

Гость 29604 имеет позицию 15.7% — ближайшая точка по часовой стрелке у `shard_0` (44.4%),
поэтому на кольце он принадлежит `shard_0`.

## 7. Сравнение стратегий

### Эксперимент 3 → 4

Тот же набор из 300 004 броней, переход 3 → 4 шарда:

|                     | Перемещено | Записей  | В новый шард | Между старыми шардами |
|---|---|---|---|---|
| `hash(key) % N`     | **75.19%** | 225 576  | 75 203       | **150 373** |
| Consistent Hashing  | **39.98%** | 119 937  | 119 937      | **0** |
| CH, 100 virtual nodes | **26.51%** | 79 531 | 79 531       | **0** |

Распределение до и после:

| Стратегия | 3 шарда | 4 шарда |
|---|---|---|
| `hash % N` | 33.2 / 33.5 / 33.3 | 25.0 / 25.1 / 24.9 / **25.1** |
| Consistent Hashing | 70.8 / 22.1 / 7.1 | 30.8 / 22.1 / 7.1 / **40.0** |
| CH, 100 vnodes | 30.5 / 31.7 / 37.9 | 23.0 / 24.7 / 25.9 / **26.5** |

### 1. Почему результаты отличаются?

Потому что у стратегий разная зависимость от числа шардов. В `hash % N` делитель `N` участвует
в вычислении шарда для **каждого** ключа, и при смене `N` пересчитывается адрес почти всех записей.
В Consistent Hashing шард ключа зависит только от ближайшей точки на кольце. Добавление шарда
ставит на кольцо новую точку, и меняется владелец только у дуги непосредственно перед ней.
Это видно в последнем столбце: у `hash % N` 150 373 брони переехали между старыми шардами,
у Consistent Hashing — **ноль**, всё перемещённое ушло только в новый шард.

### 2. Почему Consistent Hashing позволяет уменьшить объём перемещаемых данных?

Новая точка `shard_3` встала на позицию 13.3% — внутрь дуги `shard_0`. Ключи на отрезке
от 73.4% через 0% до 13.3% раньше шли по часовой стрелке до `shard_0`, а теперь первой
на их пути стоит `shard_3`. Все остальные ключи по-прежнему находят ту же ближайшую точку,
что и раньше. Поэтому переезжают только записи, которые должен забрать новый шард, и только
из одного соседа — без перетасовки остальных.

Важная деталь из измерения: консистентное хеширование гарантирует **не маленький процент**,
а **отсутствие лишних переносов**. На базовом кольце новая точка случайно захватила 40% кольца,
поэтому переехало 39.98% — ровно доля `shard_3`, не больше. С 100 virtual nodes новый шард
забирает по кусочку у каждого из старых примерно свою четверть, и перенос близок к
теоретическому минимуму 1/4: **26.51%**.

### 3. Что произойдёт, если добавить ещё один shard?

Посчитано для перехода 4 → 5 (`shard_4`):

| | Перемещено | Между старыми шардами | Доля нового шарда |
|---|---|---|---|
| `hash(key) % N` | **80.26%** | 179 966 | 20.3% |
| Consistent Hashing | **4.20%** | 0 | 4.2% |
| CH, 100 vnodes | **18.21%** | 0 | 18.2% |

- `hash % N` снова переносит почти всё. Теоретически 4/5 = **80%**: запись остаётся, только
  если `h mod 4 = h mod 5`, то есть для 4 из 20 остатков. Измерено 80.26%.
- Базовое кольцо перенесло всего 4.20%, но это плохая новость: точка `shard_4` случайно попала
  в узкую дугу, и новый сервер получил 4% данных — он почти бесполезен. Самый загруженный
  `shard_3` с 40% данных при этом не разгрузился вовсе.
- С virtual nodes новый шард получил 18.2% — близко к честной пятой части, и перенос снова
  идёт только в него.

Чем больше шардов, тем сильнее разница: для `hash % N` при переходе N → N+1 переезжает
N/(N+1) данных, то есть всё больше, а для консистентного хеширования — около 1/(N+1),
то есть всё меньше.

### 4. Что произойдёт, если удалить shard?

Посчитано для удаления `shard_1` (3 → 2):

| | Перемещено | Распределение после |
|---|---|---|
| `hash(key) % N` | **66.50%** | 49.85% / 50.15% |
| Consistent Hashing | **22.12%** | **92.91%** / 7.09% |
| CH, 100 vnodes | **31.66%** | 49.98% / 50.02% |

- `hash % N` переносит 2/3 данных (теоретически 66.7%): кроме броней удалённого шарда,
  перетасовываются ещё 98 922 записи между двумя оставшимися.
- Consistent Hashing переносит **только данные удалённого шарда**: 66 351 бронь — ровно столько,
  сколько лежало на `shard_1`. Но на базовом кольце вся дуга удалённой точки достаётся одному
  соседу по часовой стрелке. `shard_0` получил 92.91% всех данных — фактически вся система
  переехала на один сервер.
- С virtual nodes точки удалённого шарда разбросаны по кольцу, и их дуги достаются разным
  соседям: данные `shard_1` (31.66%) разошлись между двумя оставшимися поровну — 50/50.

## 8. Итог

**Shard** — отдельный независимый экземпляр PostgreSQL, который хранит часть данных таблицы;
в этой работе это три сервера, между которыми разложены 300 004 брони. **Shard key** — поле,
по значению которого определяется шард записи; здесь это `id_guest`, поэтому все брони одного
гостя лежат вместе, и запрос «брони гостя» идёт в один сервер. **Router** нужен, чтобы по ключу
вычислить, к какому экземпляру обращаться: без него приложению пришлось бы спрашивать все
шарды или хранить отдельный справочник размещения. Стратегия **`hash(key) % N`** берёт остаток
от деления хеша на число шардов и даёт идеально ровное распределение: 33.2 / 33.5 / 33.3%.
Её проблема проявляется при изменении `N`: остаток пересчитывается почти у всех ключей, и при
добавлении четвёртого шарда переехало **75.19%** данных, из них вдвое больше перетасовалось
между старыми шардами, чем досталось новому. **Consistent Hashing** решает это, размещая ключи
и шарды на кольце: новый шард забирает только дугу перед своей точкой, и переносятся только
его данные — **39.98%** на базовом кольце и **26.51%** с virtual nodes, без единой лишней записи.
При этом базовое кольцо из одной точки на шард распределило данные как 71 / 22 / 7%, а после
удаления шарда отдало одному серверу 93% данных, так что без virtual nodes его использовать нельзя.
Для своего сервиса я бы выбрал **Consistent Hashing с virtual nodes**: бронирования растут
постоянно, шарды со временем придётся добавлять, и именно при добавлении он переносит минимум
данных, сохраняя равномерность (26.5% переноса и 23–26.5% на шард после перехода).

## Ограничения текущей реализации

- **API сервиса продолжает работать с основной базой.** Router и репозиторий шардов встроены
  в проект и используются командой `shard_bookings`. Рабочие endpoint'ы на шарды не переведены:
  для этого пришлось бы также направлять через router каждую запись, а запросы без `id_guest`
  переписать на обход всех шардов.
- **Данные на шардах — снимок на момент `load`.** Брони, созданные через API позже, на шардах
  не появятся, пока `load` не выполнят повторно.
- **Перенос при смене числа шардов не выполняется, а рассчитывается.** Четвёртый и пятый шарды
  не запускались: по заданию нужно было определить, сколько записей сменит шард.
- **Смена гостя в брони.** Если `PUT /api/bookings/{id}` поменяет `id_guest`, в шардированной
  системе бронь пришлось бы удалить с одного шарда и вставить на другой.

## Как воспроизвести

```bash
docker compose up -d postgres-shard-0 postgres-shard-1 postgres-shard-2
```

## Вопросы для самопроверки

**1. Что такое shard?** Отдельный экземпляр базы данных, который хранит часть строк таблицы.
Шарды независимы: у каждого свой диск, память и процессор, и ни один не хранит данные другого.
В отличие от реплики из лабораторной №4, которая хранит полную копию, шард хранит только свою
долю — у нас по ~100 тысяч броней из 300 тысяч.

**2. Что такое shard key?** Поле записи, по значению которого определяется её шард. Он решает
сразу три вещи: насколько ровно распределятся данные, какие запросы пойдут в один шард и какие
придётся рассылать во все. У нас это `id_guest`.

**3. Почему нельзя просто случайно распределять записи между PostgreSQL?** Потому что потом
запись нужно найти. При случайном размещении у записи нет вычислимого адреса: чтобы найти брони
гостя, пришлось бы опрашивать все шарды или вести отдельный справочник «запись → шард», который
сам станет узким местом и точкой отказа. Кроме того, брони одного гостя разлетелись бы по разным
серверам. Хеширование даёт то же равномерное распределение, но детерминированно: адрес любой
записи вычисляется из её ключа за микросекунды.

**4. Как работает hash(key) % N?** Ключ превращается хеш-функцией в большое число, которое равномерно
перемешивает соседние значения, и берётся остаток от деления на число шардов. Остаток от 0 до N−1 —
номер шарда. `hash(29604) = 2898453285432545743`, остаток от деления на 3 равен 1 → `shard_1`.

**5. Почему изменение количества shard'ов является проблемой?** Потому что при другом `N` у почти
всех ключей меняется остаток, а значит и шард. Переход 3 → 4 требует перенести 75% данных
(измерено 75.19%), 4 → 5 — уже 80%. Перенос сотен гигабайт занимает часы, нагружает все серверы
одновременно, а на всё это время router должен уметь искать запись и по старому, и по новому адресу.

**6. Что такое Consistent Hash Ring?** Способ размещения, в котором хеши ключей и шардов считаются
точками на кольце — отрезке значений хеша, замкнутом в круг. Каждый ключ принадлежит первому шарду,
который встречается по кольцу после него по часовой стрелке. Шард владеет дугой от предыдущей точки
до своей.

**7. Почему при добавлении shard'а не приходится переносить все данные?** Новый шард добавляет на
кольцо одну точку и забирает только ключи на дуге перед ней, у одного соседа. Для всех остальных
ключей ближайшая точка по часовой стрелке не изменилась. Измерено: при переходе 3 → 4 между старыми
шардами не переехало ни одной записи — всё перемещённое ушло в новый шард.

**8. Что такое virtual nodes и зачем они нужны?** Это несколько точек на кольце для одного физического
шарда — у нас по 100 на шард (`hash("shard_0#0")`, `hash("shard_0#1")`, …). Одна точка на шард делит
кольцо случайными кусками: в нашем эксперименте 71 / 22 / 7%. Сотня точек дробит кольцо на множество
мелких дуг, и суммарная доля каждого шарда усредняется: 30.5 / 31.7 / 37.9%. Второй эффект ещё важнее:
при добавлении шард забирает понемногу у всех, а не всё у одного соседа, а при удалении его данные
расходятся по всем оставшимся. Без virtual nodes удаление шарда отправило 93% данных на один сервер,
с ними — 50/50. Кроме того, число точек можно сделать разным для шардов разной мощности.

**9. Может ли Consistent Hashing гарантировать идеальное распределение нагрузки?** Нет. Он гарантирует
минимальный перенос при изменении состава шардов, но не равенство долей. Базовое кольцо дало 71 / 22 / 7%;
даже с 100 virtual nodes разброс остался заметным — 30.5 / 31.7 / 37.9%, тогда как `hash % N` на тех же
данных дал 33.2 / 33.5 / 33.3%. Больше virtual nodes — ровнее, но идеальным распределение не станет.
Главное — хеш распределяет **ключи**, а не **нагрузку**: гость с тысячами броней или один очень
популярный объект целиком окажется на одном шарде при любой стратегии.

**10. Что произойдёт, если один shard станет значительно более загруженным остальных?** Система станет
работать со скоростью этого шарда: запросы к его ключам начнут замедляться, он первым исчерпает диск,
память и соединения, и его сбой затронет большую часть пользователей. Добавление нового сервера само
по себе не поможет, если он встанет на кольце не рядом с перегруженной дугой — так на базовом кольце
`shard_4` получил 4% данных, а `shard_3` с 40% не разгрузился. Решения: уменьшить число virtual nodes
у перегруженного шарда (меньше точек — меньше доля кольца) или дать больше точек новому, более мощному
серверу; разделить перегруженный шард на два; вынести горячий ключ на отдельный шард; сменить shard key,
если перекос системный.
